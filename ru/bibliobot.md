## <SolarIcon name="pin" /> Обзор проекта и задача

**BiblioBot** решает задачу подписочного распространения книг внутри Telegram. Пользователь выбирает книгу и частоту выдачи, затем получает произведение по частям — например, раз в сутки. Каталог включает бесплатные и платные книги: для платных предусмотрены демо-фрагменты, а продолжение открывается после оформления периодической подписки.

Ключевое продуктовое решение — не создавать отдельную сложную CMS. Контент-менеджер работает в привычном Google Drive: папка представляет книгу, её файлы — части, а файл свойств описывает название, категорию, тип доставки, демо-доступ и поведение выдачи. Отдельный сервис превращает эту структуру в данные, пригодные для Telegram-бота.

### <SolarIcon name="target" /> Границы решения

- показать пользователю каталог, описание книги, прогресс чтения и действия через inline-клавиатуры Telegram;
- хранить историю выдачи и не отправлять одну и ту же часть повторно;
- поддержать файлы PDF и ссылки как два типа контента;
- автоматически синхронизировать каталог, обложки и части из Google Drive;
- обрабатывать первичные платежи, рекуррентные списания, отказы и отмену подписки;
- выполнять рассылку независимо от обработки пользовательских сообщений;
- не останавливать весь продукт, если временно недоступны отдельный сервис, файл на Drive или пользовательский чат.

## <SolarIcon name="layers" /> Архитектура продукта

Вместо единого процесса система разделена по ответственности. Это позволяет независимо перезапускать, развивать и диагностировать интеграции, не блокируя пользовательский интерфейс бота из-за долгого синка Drive или временной проблемы платежного провайдера.

```text
Пользователь Telegram
        |
        v
  bibliobot — команды, меню, FSM, подписки
        |                         \
        v                          \-> payment_form — защищённая страница оплаты
SQLite + SQLAlchemy + Alembic                 |
        ^                                      v
        |                         payments_notifications — Check / Pay / Fail
        |
        +--- gdrive_parsing_service <--- Google Drive: книги, файлы, свойства
        |
        +--- books_mailer — выдача следующей части по расписанию
        +--- autopayments_notifications — предупреждения о списаниях
        +--- mails_mailer — массовые сообщения
        +--- server_health_notifications — контроль диска и maintenance-режим
```

| Сервис | Назначение | Почему выделен отдельно |
|---|---|---|

| `payment_form` | Показывает форму оплаты с виджетом CloudPayments | Карточные данные не проходят через интерфейс бота |

## <SolarIcon name="lightbulb" /> Пример наиболее сложной задачи

### Восстановление корректного платного доступа после регрессии webhook

Наиболее ответственный сценарий — не сама оплата, а согласованность всех последующих действий: успешный webhook должен обновить именно нужную запись, открыть доступ, не создать дубликат при повторной доставке события и вернуть пользователя к книге. Ошибка на любом шаге превращается в финансовую и UX-проблему: деньги списаны, но часть не приходит.

В ходе анализа регрессии были обнаружены три связанные причины: новый обработчик записывал статус успеха в legacy-формате, идентификатор первичного платежа извлекался только из одной вариации payload, а сообщения подтверждения ссылались на отсутствующие ключи. Результат — часть реально оплаченных подписок воспринималась как неоплаченная, а пользователь мог не получить ни подтверждения, ни следующего фрагмента.

::: details <SolarIcon name="code" /> Открыть разбор платёжного контура и ключевого решения

#### Разделение первичного платежа и рекуррента

Первичный платёж создаётся в БД заранее со статусом `pending`. В webhook передаются как внутренний идентификатор ожидаемой записи, так и идентификатор аккаунта. У рекуррентного платежа ожидаемая запись может отсутствовать: его связывают с уже активной подпиской и внешним `subscription_id`.

| Шаг | Первичный платёж | Рекуррентное списание |
|---:|---|---|
| **1** | Создаётся ожидаемая запись `pending` | Используется действующая `PaidSubscription` |
| **2** | `Check` сверяет сумму, аккаунт и ID платежа | Событие без invoice допускается только при наличии `subscription_id` |
| **3** | `Pay` переводит запись в успешный статус | Создаётся или переиспользуется запись по ID внешней транзакции |
| **4** | Бот отправляет подтверждение и открывает выдачу | Пользователь получает уведомление об успешном автоплатеже |

#### Устойчивое извлечение идентификатора

Провайдер может положить ID ожидаемого платежа в `data.payment_id`, `invoice_id` или `invoiceId`. Вынесенная функция приводит эти варианты к одному целому числу и возвращает `None` для некорректного значения. Так обработчики `Check` и `Pay` используют единый контракт вместо расходящихся предположений.

```python [payment_webhook_utils.py]
SUCCESS_PAYMENT_STATUSES = ("succeeded", "payed")

def extract_payment_id(notification) -> int | None:
    data = notification.data if isinstance(notification.data, dict) else {}
    value = (
        data.get("payment_id")
        or getattr(notification, "invoice_id", None)
        or getattr(notification, "invoiceId", None)
    )
    try:
        return int(str(value).strip()) if value not in (None, "") else None
    except Exception:
        return None
```

#### Совместимость без потери исторических оплат

Новые успешные платежи нормализуются в статус `succeeded`, но чтение на переходный период принимает и `succeeded`, и исторический `payed`. Это важно: исправить код недостаточно — данные, записанные прежней версией, продолжают участвовать в проверке доступа. Для выравнивания исторических строк добавлен отдельный backfill-helper, а не скрытое массовое изменение при обычном пользовательском запросе.

#### Как проверяется регрессия

- контракт подтверждает, что обработчик больше не записывает `payed` как новый статус;
- тестируется извлечение ID из трёх вариантов payload и отказ на некорректном значении;
- проверяется округление и сравнение сумм без ошибок представления `float`;
- проверяется поддержка legacy-статуса в paid-gate, аналитике и поиске последнего успешного платежа;
- отдельный контракт гарантирует, что отключённая платная подписка не порождает циклические напоминания от рассыльщика.

## <SolarIcon name="bolt" /> Технические решения и ключевые сложности

### Google Drive как контентная CMS <Badge type="tip" text="Integration" />

::: warning Проблема

Книги, их части и обложки меняются чаще, чем код. Ручная загрузка файлов в отдельную админ-панель требовала бы дублировать процесс контентной команды, а любое обновление PDF могло оставить в Telegram устаревшую закешированную версию.

:::

::: tip <SolarIcon name="lightbulb" /> Решение

Парсер трактует папку как книгу, файл свойств — как метаданные, а PDF или ключи `url.N` — как части. Номер извлекается из имени файла; дубли индексов детерминированно сдвигаются, а некорректные файлы пропускаются с записью в лог. При изменении даты модификации файла сбрасывается сохранённый Telegram `file_id`, поэтому следующая отправка заново берёт актуальный документ.

:::

### Фоновая выдача без повторов и спама <Badge type="warning" text="Scheduling" />

::: warning Проблема

Фоновый сервис должен доставлять книгу по расписанию, но не может считать каждый сбой окончательным. Пользователь мог заблокировать бота, файл мог ещё не появиться после синка, Telegram мог временно ограничить запросы, а платная подписка могла быть вручную деактивирована.

:::

::: tip <SolarIcon name="lightbulb" /> Решение

`books_mailer` сначала выбирает только активные подписки с включённой автодоставкой и повторно проверяет актуальность перед отправкой. Недоступный чат отключает рассылку только для этой подписки; отсутствие части даёт короткую отсрочку повторной попытки; временная ошибка Telegram не останавливает весь цикл. Для платных книг проверка `is_active` стоит до отправки уведомления об оплате, исключая циклический спам отключённым пользователям.

:::

### Идемпотентные webhook и честная модель статусов <Badge type="danger" text="Payments" />

::: warning Проблема

Webhook может прийти повторно, а схема событий первичной оплаты и рекуррента различается. Без единой точки нормализации повторная доставка создаёт дубли, а расхождение статусов между обработчиком и paid-gate закрывает доступ уже оплатившему пользователю.

:::

::: tip <SolarIcon name="lightbulb" /> Решение

Внешний ID транзакции выступает ключом идемпотентности. Успешные статусы нормализуются при записи, legacy-значение поддерживается при чтении, а первичные и рекуррентные события разделяются по наличию идентификаторов. Контрактные тесты фиксируют не только ответ webhook, но и связь кода обработчика с текстами, доменной логикой и поведением после оплаты.

:::

### Эксплуатация многопроцессной системы <Badge type="info" text="Operations" />

::: warning Проблема

Независимые сервисы разделяют один файл SQLite. Такой выбор упрощает развёртывание небольшого продукта, но требует аккуратного отношения к миграциям, конкурентной записи и состоянию диска.

:::

::: tip <SolarIcon name="lightbulb" /> Решение

Схема меняется через Alembic; перед миграцией в SQLite создаётся резервная копия. Docker Compose описывает сервисы и разделяемые тома явно. Отдельный мониторинг следит за диском, а при достижении порога основной mailer и middleware переходят в защитный режим. Документация задаёт безопасный путь: резервная копия, миграция, проверка инвариантов доступа и только затем релиз.

:::

4. Проверить успешное и неуспешное рекуррентное списание, отмену и изменение суммы.
5. Убедиться, что сервисы синка и рассылки живы и пишут ожидаемые логи.
6. Проверить регистрацию webhook после запуска платежного сервиса.
7. Перед любым массовым изменением статусов сделать резервную копию БД и проверить инварианты после операции.

::: details <SolarIcon name="info" /> Технические ограничения, отмеченные в проектной документации

<div class="case-source-path"><span>Источники</span><code>docs/ARCHITECTURE.md · docs/DOMAIN_AND_DATA.md · docs/OPERATIONS_AND_DEVELOPMENT.md</code></div>

- Несколько сервисов пишут в одну SQLite БД: это удобно для небольшого развёртывания, но при существенном росте нагрузки потребует оценки lock-конкуренции и возможной миграции на серверную СУБД.
- Поддержка legacy-статуса `payed` сохранена как переходная мера для исторических платежей; новые успешные записи нормализуются в `succeeded`.
- В части старых платёжных view остаются временно отключённые ветки UX — их важно рассматривать отдельно, а не включать без ревизии всего сценария.
