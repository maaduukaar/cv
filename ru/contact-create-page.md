<script setup>
import { withBase } from 'vitepress'
import { onBeforeUnmount, ref } from 'vue'

const screenshotDialog = ref(null)
const screenshotTrigger = ref(null)
const activeScreenshot = ref({
  src: '',
  alt: '',
  caption: '',
  width: 0,
  height: 0,
})

function openScreenshot(event, caption) {
  const dialog = screenshotDialog.value
  const image = event.currentTarget?.querySelector('img')

  if (!dialog || !image || typeof dialog.showModal !== 'function') {
    return
  }

  event.preventDefault()
  screenshotTrigger.value = event.currentTarget
  activeScreenshot.value = {
    src: image.currentSrc || image.src,
    alt: image.alt || '',
    caption,
    width: image.naturalWidth,
    height: image.naturalHeight,
  }

  if (!dialog.open) {
    dialog.showModal()
    document.documentElement.classList.add('case-lightbox-open')
  }
}

function closeScreenshot() {
  screenshotDialog.value?.close()
}

function handleLightboxClick(event) {
  if (event.target === event.currentTarget) {
    closeScreenshot()
  }
}

function handleLightboxClose() {
  document.documentElement.classList.remove('case-lightbox-open')
  const trigger = screenshotTrigger.value
  screenshotTrigger.value = null
  requestAnimationFrame(() => trigger?.focus({ preventScroll: true }))
}

onBeforeUnmount(() => {
  document.documentElement.classList.remove('case-lightbox-open')
})
</script>

## 📌 Обзор проекта и ТЗ

Нужно выполнить 4 доработки по усилению защиты страницы `https://example.com/contact/create`.

1. Регистрация всех пользователей с внесением данных (ИНН, КПП и др.) → Внедрить логирование данных, вводимых через форму, и их передачи в Битрикс24.
2. Двухфакторная аутентификация → Реализовать аутентификацию через Яндекс ID для всех пользователей.
3. Ограничение количества попыток ввода пароля + временная блокировка → Внедрить механизм + добавить оповещение о фактах блокировки.
4. Все доработки должны затрагивать только эту одну страницу и ни в коем случае не влиять на работу остального сайта и его функций.

::: warning Публичная версия
Исходные формулировки сохранены. Чувствительные значения заменены демонстрационными: имена участников, адреса среды и интеграций, идентификаторы, реквизиты организаций, webhook/token, email-адреса и локальные ссылки. В разделе QA доступен очищенный заполненный отчёт в DOCX.
:::

#### 000.1 — Спринт 1 — Авторизация по паролю (без 2FA) <Badge type="tip" text="Готово" />
> **Цель:** Закрыть страницу `/contact/create` простой авторизацией (логин + пароль). После этого спринта анонимный доступ к странице невозможен.

#### 000.2 — Спринт 2 — Логирование авторизации <Badge type="tip" text="Готово" />
> **Цель:** Записывать все попытки входа (успешные и неуспешные) в лог-файл для аудита и отладки.

#### 000.3 — Спринт 3 — Блокировка IP при неудачных попытках <Badge type="tip" text="Готово" />
> **Цель:** Защита от брутфорса — если с одного IP более 5 неудачных попыток за 10 минут, блокировать IP на 30 минут + оповещение.

#### 000.4 — Спринт 4 — Логирование отправки данных через форму <Badge type="tip" text="Готово" />
> **Цель:** Знать точно, какой авторизованный пользователь какие данные отправил в Битрикс24 и когда.

#### 000.4.1 — Спринт 4.1 — Унификация CSV-логирования в `/contact` <Badge type="tip" text="Готово" />
> **Цель:** Привести все CSV-логи в рамках `/contact` к единому механизму записи, чтобы авторизация, блокировки IP и логирование отправки данных использовали одну общую безопасную функцию по образцу `csv-log-template.php`.

#### 000.5 — Спринт 5 — Двухфакторная аутентификация через Email (одностраничная) <Badge type="tip" text="Готово" />
> **Цель:** Добавить второй фактор аутентификации через одноразовый код на email. Код отправляется на адрес, совпадающий с логином пользователя (дополнительное поле email не требуется). Вся логика 2FA реализуется прямо на странице `index.php` — без создания отдельной страницы.

#### 000.6 — Спринт 6 — Подключаем Яндекс.Капча к форме авторизации <Badge type="tip" text="Готово" />
> **Цель:** У нас уже была капча на форме отправки, можно её перенести на авторизацию, чтобы усложнить механические атаки.

#### 000.6.1 — Спринт 6.1 — Логирование CAPTCHA-fail и фиксация атакующего IP <Badge type="tip" text="Готово" />
> **Цель:** Не терять в аудите попытки входа, которые отклоняются до проверки пароля из-за отсутствующей или неверной Яндекс.Капчи. Такие попытки должны попадать в `auth.csv`, участвовать в rate limit и при достижении порога автоматически формировать запись в `attacks.csv`.

#### 000.7 — Спринт 7 — Полная изоляция решения в папке contact <Badge type="tip" text="Готово" />
> **Цель:** Сделать папку `contact/` полностью самодостаточным модулем, который можно перенести на любой сервер целиком, без зависимости от `php/`. Вся логика обработки формы `formXXXXXXXX`, отправки email-уведомлений, взаимодействия с Битрикс24 и логирования должна лежать внутри `contact/` и использовать собственные копии библиотек.

#### 001 — Проверка дубликатов компаний по ИНН в Bitrix CRM <Badge type="tip" text="Готово" />
> **Цель:** При выборе компании из DaData автоматически проверять наличие такой компании в Bitrix CRM по ИНН. Если дубликат найден — показать предупреждение с ID и ссылкой на компанию. Проверка происходит в реальном времени (AJAX), без перезагрузки страницы.

#### 002 — Проверка дубликатов: учёт КПП для филиалов <Badge type="tip" text="Готово" />
> **Цель:** Разрешить добавление филиалов компаний в Bitrix CRM. Сейчас проверка дубликатов сравнивает только ИНН, поэтому филиал с тем же ИНН, но другим КПП блокируется. Нужно учитывать связку ИНН+КПП — если в CRM уже есть компания с таким ИНН, но КПП отличается, это филиал, и его нужно разрешить добавить.

##### 👤 Вопрос

> "Сессии: Используем нативные сессии PHP ($_SESSION), но с усиленными настройками безопасности" -- а что это за усиленные настройки безопасности?

##### 💬 Ответ · 30 марта

Хороший вопрос. Вот что обычно подразумевается под "усиленными настройками" для PHP-сессий:

Стандартные настройки (небезопасно по умолчанию):

PHP из коробки хранит сессии в /tmp, куки живут вечно, ID сессии не обновляется, и сессию можно угнать через XSS или подделать.

Усиленные настройки — конкретно что делается:

```php
// 1. Куки только по HTTPS
ini_set('session.cookie_secure', 1);

// 2. Куки недоступны через JavaScript (защита от XSS)
ini_set('session.cookie_httponly', 1);

// 3. Куки не передаются при кросс-сайтовых запросах (защита от CSRF)
ini_set('session.cookie_samesite', 'Strict');

// 4. Время жизни куки (30 дней как указано в задаче)
ini_set('session.cookie_lifetime', 60 * 60 * 24 * 30);

// 5. Обновлять ID сессии при входе (защита от session fixation)
session_regenerate_id(true);

// 6. Хранить сессии не в /tmp а в закрытой папке
session_save_path('/secure-area/sessions');

// 7. Проверять User-Agent и IP (чтобы угнанная сессия не работала)
if ($_SESSION['user_agent'] !== $_SERVER['HTTP_USER_AGENT']) {
    session_destroy();
    // редирект на логин
}
```

Самые важные из них:

httponly и secure — обязательно, без них сессию можно украсть через JS или по HTTP.

session_regenerate_id — обязательно при логине, иначе атака session fixation.

cookie_samesite — защита от CSRF, лишним не будет.

Остальное — опционально, но добавляет уровень защиты.

##### 👤 Вопрос

> А как хранятся сессии, это физические файлы отдельные для каждого пользователя?

##### 💬 Ответ · 30 марта

Да, именно так. По умолчанию PHP хранит каждую сессию как отдельный файл на сервере.

Как это выглядит физически:

```text
/tmp/
    sess_abc123def456    ← сессия пользователя 1
    sess_xyz789ghi012    ← сессия пользователя 2
    sess_qwe456rty789    ← сессия пользователя 3
```

Имя файла = ID сессии. Этот же ID хранится в куке в браузере пользователя.

Как это работает:

```text
Браузер                          Сервер
  │                                │
  │  Cookie: PHPSESSID=abc123  →   │  открывает файл sess_abc123
  │                                │  читает данные из него
  │  ←  отвечает на запрос         │  $_SESSION['authenticated'] = true
```

Что внутри файла сессии:

```text
authenticated|b:1;username|s:5:"user";login_time|i:1700000000;
```

Просто сериализованные данные из $_SESSION.

Для нашей задачи это означает что при 30-дневной сессии файлы будут лежать на сервере 30 дней. Пользователей немного, файлов будет мало — проблем никаких. Если указать session_save_path('/secure-area/sessions') — все файлы сессий будут в одном контролируемом месте, а не в общем /tmp который доступен другим процессам на сервере.

##### 💬 Ответ · 30 марта

Скорее всего имелось в виду что init.php — это файл-инициализатор, который подключается в начале каждого PHP-файла в /secure-area/ и делает три вещи:

```php
$users = json_decode(file_get_contents(__DIR__ . '/users.json'), true);
```

```php
require_once 'config.php';
require_once 'functions.php'; // проверка сессии, логирование и т.д.
```

Чтобы в каждом файле (index.php, verify_2fa.php и т.д.) не писать одно и то же, а просто писать одну строку в начале:

```php
require_once 'init.php';

```

По сути это стандартный паттерн — единая точка входа для инициализации всего что нужно для работы модуля.

Да, company.php получает ответ от Битрикса в переменную $response, но никак его не использует — просто игнорирует:

```php

```

Что возвращает Битрикс:

При успехе:

```json
{"result":12345,"time":{"start":1234,"finish":1234}}
```

При ошибке:

```json
{"error":"ACCESS_DENIED","error_description":"Access denied!"}
```

```php
$response = file_get_contents($finalUrl);
```

В config.php добавить флаг:

```php
define('DEBUG_MODE', true);
```

```php
if (DEBUG_MODE) {

}
```

Перед выкладкой на прод просто меняешь на false — и всё debug-логирование отключается автоматически.

##### Спринт 7 — Полная изоляция решения в папке contact

> **Цель:** Сделать папку `contact/` полностью самодостаточным модулем, который можно перенести на любой сервер целиком, без зависимости от `php/`. Вся логика обработки формы `formXXXXXXXX`, отправки email-уведомлений, взаимодействия с Битрикс24 и логирования должна лежать внутри `contact/` и использовать собственные копии библиотек.
> **Ограничение:** Затрагивается **только** кейс `formXXXXXXXX` (форма `/contact/create`). Все остальные ~25 форм сайта продолжают работать через `php/forms.php` без изменений.

###### Архитектурное решение

Сейчас форма `contact/create.php` отправляет POST на `/procces/`, который обрабатывается глобальным роутером `php/forms.php`. Внутри `forms.php` кейс `formXXXXXXXX` использует:

1. **`sendEmails()`** — функция из `php/forms.php`, использует `php/PHPMailer/`
2. **`php/bitrix/company.php`** — формирует запрос к Bitrix REST API
3. **`logCompanyFormData()`** — из `company.php`, уже пишет в `contact/login/logs/`
4. **`logFormData()`** — общий CSV-лог из `php/forms.php`
5. **`sanitizeInput()`, `detectInjection()`, `validateFields()`, `checkRateLimit()`** — защитные функции из `php/forms.php`
6. **`initContactCreateAuthSession()`** — проверка авторизации (обратная ссылка на `contact/login/init.php`)
7. **`sanitizeCsvValue()`, `logErrorData()`, `getRealIp()`** — вспомогательные функции

После спринта 10 вся эта цепочка будет жить внутри `contact/` и обслуживаться собственным обработчиком `contact/process.php`.

```php:line-numbers [csv-log-template.php]
// БЕЗОПАСНАЯ ФУНКЦИЯ ЛОГИРОВАНИЯ С БЛОКИРОВКОЙ ФАЙЛА
function logPdnConsentData($user): bool {
    // 1. Директория для логов
    global $CFG;
    $baseLogDir = $CFG->dataroot . '/pdnconsent'; // -- /moodledata/pdnconsent

    // Проверка: существует ли папка и доступна ли для записи
    if (!is_dir($baseLogDir) || !is_writable($baseLogDir)) {
        // Пишем в системный лог сервера, так как в файл писать не можем
        error_log("CRITICAL ERROR: Directory $baseLogDir does not exist or is not writable!");
        return false;
    }

    // 2. Имя файла с ротацией по МЕСЯЦАМ
    $currentMonth = date('Y-m');
    $logFile = $baseLogDir . '/forms_log_' . $currentMonth . '.csv';

    // 3. Ограничение размера файла (5 МБ)
    $maxFileSize = 5 * 1024 * 1024;

    // Очищаем кэш состояния файлов (важно для точного определения размера)
    clearstatcache(true, $logFile);

    // Логика ротации (архивации): если файл превысил лимит — переименовываем
    if (file_exists($logFile) && filesize($logFile) > $maxFileSize) {
        $backupName = $baseLogDir . '/forms_log_' . $currentMonth . '_backup_' . date('His') . '.csv';
        if (!rename($logFile, $backupName)) {
            error_log("ERROR: Could not rotate log file $logFile to $backupName");
        }
    }

    // 4. Открываем файл в режиме добавления (append)
    $file = fopen($logFile, 'a');
    if (!$file) return false;

    // --- НАЧАЛО БЛОКИРОВКИ (LOCK_EX) ---
    // Предотвращает смешивание строк при одновременной отправке форм несколькими людьми
    if (flock($file, LOCK_EX)) {

        // Добавляем BOM и заголовки, если файл новый (проверяем размер уже после блокировки)
        clearstatcache(true, $logFile);
        if (filesize($logFile) === 0) {
            // BOM нужен для корректного отображения кириллицы в Excel
            fprintf($file, chr(0xEF).chr(0xBB).chr(0xBF));
            fputcsv($file, [
                'Дата', 'Название формы', 'ФИО', 'Email', 'Телефон', 'IP адрес', 'URL страницы', 'Согласие'
            ], ';');
        }

        // --- Безопасный IP ---
        $ip = $_SERVER['REMOTE_ADDR'] ?? '0.0.0.0';
        if (!empty($_SERVER['HTTP_X_FORWARDED_FOR'])) {
            $forwarded = explode(',', $_SERVER['HTTP_X_FORWARDED_FOR']);
            $firstIp = trim($forwarded[0]);
            // Валидация IP (защита от подмены заголовков)
            if (filter_var($firstIp, FILTER_VALIDATE_IP, FILTER_FLAG_NO_PRIV_RANGE | FILTER_FLAG_NO_RES_RANGE)) {
                $ip = $firstIp;
            }
        }
        // Оставляем только допустимые символы в IP
        $ip = preg_replace('/[^0-9a-fA-F:.]/', '', $ip);

        // --- Очистка и подготовка данных ---
        // Проверяем referer на валидность URL, иначе подставляем заглушку
        $referer = $_SERVER['HTTP_REFERER'] ?? '-';
        $safeReferer = filter_var($referer, FILTER_VALIDATE_URL) ? sanitizePdnCsvValue($referer) : 'Direct/Invalid';

        // Факт согласия берём из объекта $user — поле pdnconsent передаётся из формы
        $consent = !empty($user->pdnconsent) ? 'ДА' : 'НЕТ';

        // Формируем строку лога
        $logRow = [
            date('Y-m-d H:i:s'),
            'Форма регистрации на сайте learning.example.com',
            sanitizePdnCsvValue($user->fullname ?? 'N/A'),
            sanitizePdnCsvValue($user->email    ?? 'N/A'),
            sanitizePdnCsvValue($user->phone    ?? 'N/A'),
            $ip,
            $safeReferer,
            $consent,
        ];

        // Записываем строку в CSV
        fputcsv($file, $logRow, ';');

        // Снимаем блокировку
        flock($file, LOCK_UN);
    }
    // --- КОНЕЦ БЛОКИРОВКИ ---

    fclose($file);
    return true;
}

// ФУНКЦИЯ МАКСИМАЛЬНОЙ ЗАЩИТЫ ДЛЯ CSV
function sanitizePdnCsvValue($text) {
    if (is_array($text)) return '[Array]';

    // 1. Убираем лишние пробелы и табуляцию
    $text = trim((string)$text);

    // 2. Убираем переносы строк (критично для CSV)
    $text = str_replace(["\r", "\n", "\t"], " ", $text);

    // 3. Защита от XSS
    $text = htmlspecialchars($text, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');

    // 4. Защита от CSV Injection (формул Excel)
    if ($text !== '' && in_array($text[0], ['=', '+', '-', '@'])) {
        $text = "'" . $text;
    }

    return $text;
}
```

##### 2. Доступные методы Bitrix REST API

###### Метод 1: `crm.company.list` (⭐ Рекомендуемый)

Позволяет искать компании по **любым полям**, включая пользовательские (UF_CRM_*).

```http
GET /rest/.../crm.company.list?
    filter[UF_CRM_INN]=1234567890
    &select[]=ID
    &select[]=TITLE
    &select[]=UF_CRM_INN
```

> **💡 Рекомендация.** Это **лучший вариант** для нашего проекта, потому что форма собирает ИНН и ОГРН — уникальные идентификаторы юридических лиц. Точное совпадение по ИНН = гарантированный дубль.

###### Метод 2: `crm.duplicate.findbycomm`

Ищет дубликаты по **телефону или email**.

```http
GET /rest/.../crm.duplicate.findbycomm?
    entity_type=COMPANY
    &type=PHONE
    &values[]=+7XXXXXXXXXX
```

> **⚠️ Ограничение.** Этот метод **не подходит как основной**, потому что форма `contact/create` **не собирает телефон и email компании**. Однако, если эти поля будут добавлены в будущем — его можно подключить как дополнительную проверку.

###### Метод 3: `crm.company.list` по названию (fuzzy)

Ищет по частичному совпадению названия:

```http
GET /rest/.../crm.company.list?
    filter[%TITLE]=Ростелеком
    &select[]=ID
    &select[]=TITLE
```

> **ℹ️ Примечание.** Полезен как **дополнительная** проверка, но ненадёжен из-за вариаций в написании ("ООО Ростелеком" vs "Ростелеком ООО" vs "ПАО «Ростелеком»").

##### 3. Рекомендуемая стратегия

###### Комбинированная проверка перед `crm.company.add`

```text
Получены данные формы
        ↓
ИНН заполнен?
├── Да  → crm.company.list по ИНН ──┐
└── Нет → crm.company.list по TITLE ┤
                                      ↓
                              Компании найдены?
                              ├── Нет → crm.company.add
                              └── Да  → Предупреждение + список дублей
                                         ├── Подтвердить → crm.company.add
                                         └── Отмена
```

###### Два режима работы

**Режим A — Блокирующий (строгий):**
- Если найден дубль по ИНН → **запретить** создание, показать ссылку на существующую компанию
- Простой в реализации, но негибкий

**Режим B — Предупреждающий (рекомендуемый):**
- Если найден дубль → **показать предупреждение** со списком похожих компаний
- Пользователь сам решает: создать новую или перейти к существующей
- Требует AJAX-запрос перед отправкой формы

##### 4. Пример реализации (PHP)

###### Новая функция поиска дубликатов

Добавляется в `bitrix_company.php`:

```php
/**
 * Ищет существующие компании в Bitrix CRM по ИНН и/или названию.
 *
 * @param array $formData данные формы
 * @return array ['found' => bool, 'companies' => [...]]
 */
function contactFindDuplicateCompanies(array $formData) {
    $config = function_exists('contactLoginGetConfig')
        ? contactLoginGetConfig()
        : require dirname(__DIR__) . '/config.php';
    
    $apiUrl = rtrim((string) ($config['bitrix_rest_api_url'] ?? ''), '/');
    $isMockMode = !empty($config['bitrix_mock_mode']);
    
    if ($apiUrl === '') {
        return ['found' => false, 'companies' => [], 'error' => 'api_not_configured'];
    }
    
    // Приоритет 1: поиск по ИНН (точное совпадение)
    $inn = contactBitrixGetFormFieldValue($formData, 'inn');
    
    if ($inn !== '') {
        $result = contactBitrixSearchCompanyByField($apiUrl, 'UF_CRM_INN', $inn, $isMockMode);
        
        if (!empty($result['companies'])) {
            return $result;
        }
    }
    
    // Приоритет 2: поиск по названию (частичное совпадение)
    $title = contactBitrixGetFormFieldValue($formData, 'company');
    
    if ($title !== '') {
        return contactBitrixSearchCompanyByField($apiUrl, '%TITLE', $title, $isMockMode);
    }
    
    return ['found' => false, 'companies' => []];
}

/**
 * Выполняет поиск компании по одному полю через crm.company.list.
 */
function contactBitrixSearchCompanyByField($apiUrl, $fieldName, $value, $isMockMode = false) {
    if ($isMockMode) {
        return ['found' => false, 'companies' => [], 'is_mock' => true];
    }
    
    $requestUrl = $apiUrl . '/crm.company.list?'
        . 'filter[' . urlencode($fieldName) . ']=' . urlencode($value)
        . '&select[]=ID&select[]=TITLE&select[]=UF_CRM_INN';
    
    $httpContext = stream_context_create([
        'http' => [
            'method'  => 'GET',
            'timeout' => 10,
            'ignore_errors' => true,
        ],
    ]);
    
    $responseRaw = @file_get_contents($requestUrl, false, $httpContext);
    
    if ($responseRaw === false) {
        return ['found' => false, 'companies' => [], 'error' => 'request_failed'];
    }
    
    $decoded = json_decode($responseRaw, true);
    $companies = is_array($decoded) && isset($decoded['result']) ? $decoded['result'] : [];
    
    return [
        'found'     => count($companies) > 0,
        'companies' => $companies,
    ];
}
```

Вставка **перед** вызовом `contactCreateBitrixCompany()` на `строке 296`:

##### 6. Возможные риски и ограничения

> **⚠️ Rate limits Bitrix REST API.** Вебхук ограничен **2 запросами в секунду** (стандартный лимит Bitrix24). Каждая проверка дубликатов — это +1 запрос перед созданием. При текущей нагрузке это **не проблема**, но стоит учитывать.

> **ℹ️ Mock-режим.** Сейчас `bitrix_mock_mode = true` в конфиге. В mock-режиме проверку дублей можно безопасно пропускать (возвращать `found: false`), что уже учтено в примере кода выше.

> **❗ Кастомные поля (`UF_CRM_*`).** Поиск по ИНН использует кастомное поле `UF_CRM_INN`. Если его ID изменится на стороне Bitrix — поиск дубликатов сломается. Но тот же риск уже существует для `crm.company.add`, так что это не новая проблема.

#### [001] Проверка дубликатов компаний по ИНН в Bitrix CRM

> **Цель:** При выборе компании из DaData автоматически проверять наличие такой компании в Bitrix CRM по ИНН. Если дубликат найден — показать предупреждение с ID и ссылкой на компанию. Проверка происходит в реальном времени (AJAX), без перезагрузки страницы.

##### Архитектура решения

| Шаг | Участник | Действие / ответ |
|:---:|---|---|
| 1 | Пользователь → Форма | Начинает вводить название компании |
| 2 | Форма → DaData API | Отправляет Suggestions API запрос |
| 3 | DaData API → Форма | Возвращает список подсказок |
| 4 | Пользователь → Форма | Выбирает компанию из списка |
| 5 | Форма | DaData заполняет ИНН, ОГРН, КПП и другие скрытые поля |
| 6 | Форма | `onSelect` получает ИНН и блокирует кнопку текстом «Проверка...» |
| 7 | Форма → endpoint | AJAX GET на `/contact/check-duplicate.php?inn=1234567890` |
| 8 | Endpoint | Проверяет авторизацию |
| 9 | Endpoint → Bitrix REST API | Запрашивает `crm.company.list` с фильтром по ИНН |
| 10 | Bitrix REST API → Endpoint | Возвращает JSON: найдено / не найдено |
| 11 | Endpoint → Форма | Возвращает `{found: true/false, companies: [...]}` |
| 12А | Форма · дубль найден | Показывает предупреждение; кнопка остаётся заблокированной |
| 12Б | Форма · дубль не найден | Убирает предупреждение и разблокирует кнопку |

##### Задачи

###### Бэкенд

- ⬜ **1.1** Создать функцию поиска дубликата по ИНН в `bitrix_company.php`
  - Новая функция `contactFindDuplicateByInn(string $inn): array`
  - Использует метод Bitrix REST API `crm.company.list` с фильтром по кастомному полю ИНН (`UF_CRM_INN`)
  - Запрашивает поля: `ID`, `TITLE`, `UF_CRM_INN` (ИНН)
  - Таймаут HTTP-запроса: **5 секунд** (быстрее стандартных 10, чтобы не тормозить UI)
  - В mock-режиме (`bitrix_mock_mode = true`) — всегда возвращает `found: false`
  - Формат ответа:
    ```php
    [
        'found'     => bool,
        'companies' => [['ID' => '12345', 'TITLE' => 'ООО Рога и Копыта', 'UF_CRM_INN' => '1234567890']],
        'error'     => null | 'request_failed' | 'api_not_configured',
        'is_mock'   => bool,
    ]
    ```

- ⬜ **1.2** Создать AJAX-эндпоинт `contact/check-duplicate.php`
  - Принимает: `GET ?inn=XXXXXXXXXX`
  - Проверка авторизации: `contactLoginIsAuthenticated()` — если нет → `{"error": "auth_required"}`
  - Валидация ИНН: только цифры, длина 10 или 12 символов (`/^\d{10}(\d{2})?$/`)
  - Если ИНН невалидный → `{"found": false, "companies": []}`
  - Вызывает `contactFindDuplicateByInn($inn)`
  - При успешном поиске возвращает массив найденных компаний с полями:
    - `id` — ID компании в Bitrix
    - `title` — название компании
    - `inn` — ИНН компании
    - `url` — прямая ссылка на карточку: `https://crm.example.com/crm/company/details/{ID}/`
  - Заголовки: `Content-Type: application/json; charset=utf-8`
  - `no-cache` заголовки, чтобы браузер не кешировал ответ

- ⬜ **1.3** Зарегистрировать маршрут `/contact/check-duplicate.php`
  - В `router.php`: добавить кейс `'/contact/check-duplicate.php'`
  - В массив `$dynamicPhpRoutes`: добавить путь
  - В `.htaccess` (корневой): добавить `RewriteRule ^contact/check-duplicate\.php$ contact/check-duplicate.php [NC,L]`

###### Фронтенд

- ⬜ **1.4** Добавить AJAX-проверку дубликата в `onSelect` callback DaData
  - В `create.php` (блок DaData, строка ~2226, функция `onSelect`) **после** заполнения скрытых полей добавить вызов новой функции `checkDuplicateByInn(inn)`
  - Функция `checkDuplicateByInn(inn)`:
    1. Если `inn` пустой или не проходит regex `/^\d{10,12}$/` — не делать запрос, выйти
    2. Заблокировать кнопку «Отправить»: `submitBtn.disabled = true`, текст → `"Проверка..."`
    3. Скрыть предыдущее предупреждение (если было)
    4. Выполнить `fetch('/contact/check-duplicate.php?inn=' + encodeURIComponent(inn))`
    5. **Таймаут на фронте — 8 секунд** (через `AbortController`). Если запрос не успел — показать кнопку «Пропустить проверку»
    6. При получении ответа:
       - Если `found === true` → показать жёлтый блок предупреждения, кнопка остаётся заблокированной
       - Если `found === false` → убрать предупреждение, разблокировать кнопку
       - Если ошибка сети или таймаут → разблокировать кнопку (не блокировать работу из-за сбоя проверки), показать ненавязчивое уведомление

- ⬜ **1.5** Создать блок предупреждения о дубликате
  - HTML-контейнер `<div id="duplicate-warning">` — вставляется **над** полем поиска компании (перед `<div class="t-input-group" data-input-lid="INPUT_ID">`)
  - Стили предупреждения:
    - Фон: `#FFF3CD` (жёлтый, как Bootstrap `alert-warning`)
    - Граница: `1px solid #FFEEBA`
    - Скруглённые углы: `border-radius: 4px`
    - Иконка ⚠️ слева
    - Текст: **«Данная компания уже добавлена в Bitrix CRM»**
    - Под текстом: **ID компании** и **кликабельная ссылка** на карточку (открывается в новой вкладке)
    - Ссылка на карточку стилизована как кнопка-ссылка (синий текст, подчёркивание)
    - Анимация появления: плавное раскрытие вниз (`max-height` transition, ~300ms)
    - Кнопка закрытия `×` (только убирает предупреждение из UI, разблокирует кнопку «Отправить» — это сценарий сознательной попытки добавить «дубль»)
  - При скрытии предупреждения (по `×`) — разблокировать кнопку «Отправить» (пользователь сознательно игнорирует предупреждение)
  - Пример визуала:
    ```
    ┌──────────────────────────────────────────────────────┐
    │ ⚠️ Данная компания уже добавлена в Bitrix CRM    [×] │
    │                                                      │
    │    Компания: ООО «Ростелеком»                        │
    │    ID: 12345                                         │
    │    🔗 Открыть карточку в CRM                         │
    └──────────────────────────────────────────────────────┘
    ```

- ⬜ **1.6** Реализовать обработку «зависания» проверки (защита от долгих запросов)
  - Если AJAX-запрос длится дольше **8 секунд**:
    1. Отменить запрос через `AbortController.abort()`
    2. Показать серый информационный блок (вместо жёлтого): *«Проверка дубликатов недоступна. Вы можете продолжить без проверки.»*
    3. Разблокировать кнопку «Отправить» (позволить работать в обычном режиме)
  - Если произошла сетевая ошибка (`fetch` rejected, не таймаут) — аналогично: не блокировать пользователя, показать ненавязчивое сообщение
  - **Принцип:** Проверка дубликатов — опциональная «надстройка». Она **никогда** не должна полностью блокировать работу формы

- ⬜ **1.7** Убрать предупреждение при сбросе формы
  - После успешной отправки формы (вместе с `form.reset()`) — скрывать блок `#duplicate-warning`
  - При ручном изменении поля «Название компании» (повторный ввод) — скрывать блок предупреждения  
  - При начале нового ввода в поле DaData (до нового `onSelect`) — скрывать старое предупреждение

###### Защита и безопасность

- ⬜ **1.8** Валидация на стороне `check-duplicate.php`
  - ИНН — только цифры, 10 или 12 символов. Иначе → `{"found": false}`
  - Проверка авторизации обязательна. Неавторизованный запрос → `{"error": "auth_required"}`
  - Rate limit не требуется (проверка привязана к действиям пользователя и ограничена UX-потоком, а на уровне Bitrix API уже есть лимит 2 rps)

##### Особенности и подводные камни

> **DaData `onSelect` — единственная точка входа.**
> ИНН попадает в скрытое поле только при выборе подсказки из DaData. Пользователь не вводит ИНН вручную. Поэтому проверку вызываем именно в колбэке `onSelect`, а не по `input` событию.

> **Mock-режим.**
> Сейчас `bitrix_mock_mode = true`. В mock-режиме проверка всегда возвращает `found: false`. Это безопасно — не блокирует разработку. При переключении на `false` проверка заработает автоматически.

> **Кастомное поле `UF_CRM_INN`.**
> Это тот же ID, который уже используется в `contactBitrixGetFieldMap()` для `crm.company.add`. Если он изменится — сломается и добавление, и проверка. Новых рисков нет.

> **Порядок: сначала DaData заполняет поля, потом вызываем проверку.**
> Важно, чтобы `checkDuplicateByInn()` вызывался **после** строки `$("input[name='inn']").val(suggestion.data.inn)`, а не до неё.

##### Критерий завершения (DoD)

- ⬜ При выборе компании из DaData автоматически уходит AJAX-запрос на проверку по ИНН
- ⬜ Кнопка «Отправить» блокируется на время проверки с текстом «Проверка...»
- ⬜ Если дубликат найден — появляется жёлтое предупреждение с ID и ссылкой на карточку в CRM
- ⬜ Предупреждение можно закрыть вручную (по `×`), после чего кнопка разблокируется
- ⬜ Если дубликат не найден — кнопка разблокируется, предупреждение не показывается
- ⬜ Если проверка зависла (>8 сек) или упала — пользователь может продолжить работу без проверки
- ⬜ Неавторизованный запрос на `/contact/check-duplicate.php` возвращает ошибку
- ⬜ В mock-режиме проверка не блокирует форму (всегда `found: false`)
- ⬜ Повторный ввод названия компании сбрасывает предыдущее предупреждение

## 9. Учёт КПП для филиалов <Badge type="tip" text="Готово" />



::: details 🏢 Открыть задачу учёта КПП

<div class="case-source-path"><span>Источник</span><code>.tasks/done/002-duplicate-kpp-branch/task.md</code></div>

#### [002] Проверка дубликатов: учёт КПП для филиалов

> **Цель:** Разрешить добавление филиалов компаний в Bitrix CRM. Сейчас проверка дубликатов сравнивает только ИНН, поэтому филиал с тем же ИНН, но другим КПП блокируется. Нужно учитывать связку ИНН+КПП — если в CRM уже есть компания с таким ИНН, но КПП отличается, это филиал, и его нужно разрешить добавить.

##### Контекст проблемы

Обращение пользователя:
> «Не хочет добавлять в Битрикс, из-за того что есть компания с данным ИНН, но мне нужен филиал, ИНН/КПП 9876543210/987654321»

На скриншоте видно:
- Система нашла компанию **ООО «Пример»** (ID: 12345) с ИНН `9876543210`
- Пользователь пытается добавить **ФИЛИАЛ «Пример»** с тем же ИНН, но другим КПП (`987654321`)
- Кнопка «Отправить» заблокирована, предупреждение не даёт добавить филиал

###### Почему так происходит

Текущая логика в `contactFindDuplicateByInn()` (`bitrix_company.php:414`) ищет компании **только по ИНН** через `crm.company.list` с фильтром `UF_CRM_INN`. КПП (`UF_CRM_KPP`) не участвует ни в запросе, ни в сравнении.

У филиалов одного юрлица **ИНН всегда совпадает** с головной организацией. Отличается только **КПП** (код причины постановки на учёт — первые 4 цифры указывают на налоговый орган, 5-6 цифры — причина).

| Запись | ИНН | КПП | Результат сравнения |
|---|---|---|---|
| Головная организация | `9876543210` | `123456789` (пример) | Базовая запись |
| Филиал | `9876543210` | `987654321` | КПП отличается → это другая запись |

##### Задачи

###### Бэкенд

- ✅ **2.1** Расширить `check-duplicate.php` — принимать параметр `kpp`
  - Добавить `$kpp = isset($_GET['kpp']) ? trim((string) $_GET['kpp']) : '';`
  - Передать КПП в функцию поиска дубликатов
  - Валидация КПП: 9 цифр (`/^\d{9}$/`) — если не проходит, КПП просто игнорируется (не блокирует проверку)

- ✅ **2.2** Расширить `contactFindDuplicateByInn()` → `contactFindDuplicate()` (или добавить параметр `$kpp`)
  - Сигнатура: `contactFindDuplicateByInn(string $inn, string $kpp = ''): array`
  - Добавить в запрос `crm.company.list` поле КПП в `select[]`: `UF_CRM_KPP`
  - **Логика сравнения после получения ответа от Bitrix:**
    1. Получаем список компаний с совпадающим ИНН (как сейчас)
    2. Если `$kpp` передан и непустой — фильтруем результат: оставляем **только** компании, у которых КПП **точно совпадает** с переданным `$kpp`
    3. Если после фильтрации по КПП список пуст → `found: false` (это филиал, его можно добавить)
    4. Если `$kpp` пустой — поведение не меняется (обратная совместимость)

  - Добавить `UF_CRM_KPP` в нормализацию (аналогично ИНН)
  - В `check-duplicate.php` добавить `kpp` в ответный объект каждой компании

###### Фронтенд

  - КПП заполняется DaData при выборе компании (поле `suggestion.data.kpp`)

- ✅ **2.5** Обновить текст предупреждения — показывать КПП найденных компаний
  - В блоке предупреждения рядом с ИНН добавить строку **КПП: XXXXXXXXX**

  - Компания с тем же ИНН и тем же КПП → добавление **заблокировано** (настоящий дубликат)

##### Особенности и подводные камни

> **КПП у ИП отсутствует.**
> У индивидуальных предпринимателей КПП нет. Если КПП пустой — проверку нужно оставить как есть (только по ИНН). Фильтрация по КПП срабатывает **только** если КПП реально передан.

> **КПП может не быть в Bitrix.**
> Если у существующей компании в CRM поле КПП (`UF_CRM_KPP`) не заполнено — её нельзя исключить из дублей, потому что мы не знаем КПП. В этом случае она остаётся в списке найденных (считаем потенциальным дубликатом).

> **Обратная совместимость.**
> Параметр `kpp` в `check-duplicate.php` — опциональный. Без него поведение полностью совпадает с текущим. Это важно, чтобы не сломать работу если фронтенд не обновился.

> **Кнопка закрытия `×` остаётся.**
> Даже если проверка по ИНН+КПП нашла точный дубликат, пользователь всё ещё может закрыть предупреждение и отправить форму. Это сознательное решение из задачи 001 — проверка предупреждающая, не блокирующая.

## 10. Финальный отчёт, деплой и оповещение <Badge type="tip" text="REPORT.md" />



::: details 🏁 Открыть финальный отчёт

Все пункты задачи выполнены:

1. Авторизация — реализована в папке `contact/login/`. Логин + пароль, хеши через `password_hash()` (bcrypt), пользователи в `users.json`. Сессия живёт 30 дней с усиленными настройками (`httponly`, `secure`, `samesite=Strict`, `session_regenerate_id`). Анонимный доступ к `/contact/create` невозможен — идёт редирект на форму входа.

2. Двухфакторная аутентификация — реализована через email (одноразовый 6-значный код). После ввода верного пароля поля становятся readonly, под ними появляется поле для кода. Код живёт 5 минут, повторная отправка — не чаще 1 раза в 60 секунд, максимум 5 попыток ввода. Включается/выключается глобально в `config.php` (`2fa_global_enable`) и персонально в `users.json` (`2fa_enabled`). Все параметры вынесены в конфигурацию.

3. Блокировка IP — если с одного IP более 5 неудачных попыток за 10 минут, IP блокируется на 30 минут. Данные хранятся в `login_attempts.json`, устаревшие записи автоматически очищаются. При блокировке событие записывается в `attacks.csv` с деталями: IP, User-Agent, перебираемые логины, время окончания блокировки, proxy-заголовки.

4. Логирование — реализовано по стандартному образцу (CSV с ротацией по месяцам, flock при записи, BOM, санитизация от CSV Injection). Ведутся 4 лога:
   - `auth_YYYY-MM.csv` — все попытки входа (время, IP, UA, логин, результат)
   - `attacks_YYYY-MM.csv` — факты блокировки IP
   - `bitrix_data_YYYY-MM.csv` — какой пользователь какие данные отправил в Битрикс и что Битрикс ответил
   - `form_errors_YYYY-MM.csv` — ошибки валидации, rate limit, инъекции, сбои SMTP и Битрикс API
   Все логи хранятся в `contact/login/logs/`, доступ к ним из браузера закрыт через `.htaccess`.

Архитектура — вся логика вынесена в отдельную папку `contact/`. Папка полностью автономна: собственный PHPMailer, собственная SMTP-конфигурация, собственный POST-обработчик `contact/process.php`. Модуль можно целиком перенести на другой сервер — при наличии PHP, доступа к SMTP и Битрикс API он полностью функционален. Остальные ~25 форм сайта продолжают работать через `php/forms.php` без изменений.

Дополнительные меры:

1. CSRF-защита — все POST-формы защищены уникальным токеном. Сравнение через `hash_equals` (защита от timing-атак). Токен ротируется при входе и на шаге 2FA.

2. Яндекс SmartCaptcha на форме входа — перенесена с формы отправки на страницу авторизации. CAPTCHA-fail считается неудачной попыткой входа и участвует в блокировке IP.

3. Полная изоляция модуля — задача подразумевала работу в изолированной папке, но реальных зависимостей от `php/` было больше чем ожидалось.
