# 📄 Создание кейс-страниц портфолио из проектных материалов

Этот скилл описывает полный пайплайн превращения рабочих `.tasks`, `.review` и `.report` файлов проекта в готовые публичные страницы-кейсы портфолио для VitePress.

---

## 📥 1. Сбор и анализ исходных материалов

### Источники данных

При получении запроса на создание кейс-страницы — сначала проанализируй все доступные материалы:

| Директория | Что содержит | Что извлекать |
|---|---|---|
| `.tasks/` | Файлы задач в формате `NN-slug.md` | ТЗ, декомпозиция, критерии приёмки (DoD) |
| `.tasks/done/` | Завершённые задачи | Полный список выполненных работ, код решений |
| `.tasks/cancelled/` | Отменённые задачи | Контекст отмены (↩️ в таблице задач) |
| `.review/` | Ревью кода, обратная связь | Найденные баги, архитектурные замечания, решения |
| `.report/` | Финальные отчёты | Результаты тестирования, метрики, итоги |

### Порядок анализа

1. Прочитай `README.md` в `.tasks/` (если есть) — там описана система именования.
2. Просмотри все файлы в `.tasks/done/` — это основной источник контента.
3. Проверь `.tasks/cancelled/` — отменённые задачи дают контекст эволюции решения.
4. Прочитай `.review/` — ревью содержат описания проблем и рекомендации.
5. Прочитай `.report/` — отчёты содержат метрики и результаты тестирования.

## 🏗️ 2. Структура кейс-страницы

Каждая страница **обязательно** следует стандартам скилла `vitepress-article-formatter`. Прочитай его перед началом работы.

### Обязательные секции (в порядке следования)

```markdown
# Заголовок <Badge type="tip" text="Стек" /> <Badge type="warning" text="Технология" />

::: info 📋 Карточка проекта
| | |
|---|---|
| **Стек** | ... |
| **Роль** | ... |
| **Ключевые файлы** | `file1.php`, `file2.js` |
| **Сайт** | 🔗 [Название](https://example.com/) |
| **Результат** | Одно предложение с главным достижением |
:::

## 📌 Обзор проекта и ТЗ
  → Описание проблемы / Исходное состояние
  → Технический анализ причин (если применимо)
  → Техническое задание (ТЗ) — границы задачи

## 📋 Полный список задач
  → Таблица: № / Задача / Описание [/ Статус]

## 💡 Пример наиболее сложной задачи
  → ::: details с полным разбором одной задачи

## ⚡ Технические решения и ключевые сложности
  → ::: warning Проблема → ::: tip 💡 Решение (пары)

## 📈 Итоговые результаты
  → ::: tip 🏆 Таблица метрик До / После
```

## 📊 3. Форматирование списка задач

Есть два формата оформления. Выбор зависит от масштаба проекта.

### 🏆 Идеальный формат (для крупных проектов, 10+ задач)

Используется в эталонной странице `r7-document-api.md`. Каждая задача — это **заголовок `####`** с бейджем статуса и **блоком цитаты `>`** с описанием цели. Весь реестр задач оборачивается в `::: details`.

Группировка задач по категориям:
1. **Выполненные задачи разработки** — `<Badge type="tip" text="Done" />`
2. **Задачи этапа Код-Ревью** — `<Badge type="info" text="Code Review" />`
3. **Отменённые / пересмотренные** — `<Badge type="warning" text="Cancelled" />`
4. **Запланированный бэклог** — `<Badge type="warning" text="Later" />`

````markdown
## 📋 Полный реестр инженерных задач проекта (`.tasks`)

::: details 📋 Посмотреть полный перечень всех N задач проекта с целями

### 🚀 1. Выполненные задачи разработки (`.tasks/done/`)

#### 01 — MVP: дочерняя тема с кастомным шаблоном рубрики <Badge type="tip" text="Done" />
> **Цель:** Сделать минимально рабочую реализацию через дочернюю тему WordPress,
> чтобы для рубрики использовался кастомный шаблон. Шаблон должен выводить список
> всех дочерних рубрик, их описание, а также заголовки и краткие описания статей.

#### 02 — Поддержка term meta для подрубрик <Badge type="tip" text="Done" />
> **Цель:** Расширить MVP: добавить три дополнительных поля `term meta`
> и изменить кастомный шаблон для их вывода.

---

### 🔍 2. Задачи этапа Код-Ревью

#### R-01 — Добавить проверку nonce в сохранение <Badge type="info" text="Code Review" />
> **Цель:** Защитить сохранение term meta от программных вызовов
> с устаревшими данными в `$_POST`.

---

### ⚠️ 3. Отменённые / Архитектурно пересмотренные задачи

#### C-06 — Ограничить показ полей только для нужных веток <Badge type="warning" text="Cancelled" />
> **Цель:** *(Архитектурно пересмотрено)* Доработать плагин, чтобы поля
> отображались не для всех рубрик, а только для конкретных корневых разделов.

:::
````

**Ключевые правила идеального формата:**

- Заголовок задачи: `#### NN — Краткое название <Badge type="..." text="..." />`
- Описание: цитата `>` с **Цель:** жирным в начале
- Для отменённых задач: курсив `*(причина отмены)*` перед описанием цели
- Группировка: `### 🚀 / 🔍 / ⚠️ / 📌` с указанием папки-источника
- Всё оборачивается в один `::: details` с числом задач в заголовке

### 📊 Компактный формат (для небольших проектов, до 10 задач)

Используется таблица — без обёртки в `::: details`.

```markdown
## 📋 Полный список задач

| № | Задача | Описание |
|:---:|---|---|
| 01 | **Название задачи** | Краткое описание результата |
| 02 | **Другая задача** | Краткое описание результата |
```

Со столбцом статуса (если есть отменённые):

```markdown
| № | Задача | Описание | Статус |
|:---:|---|---|:---:|
| 03 | **Исследование подхода A** | Отменено в пользу подхода B | ↩️ |
| 03-1 | **Реализация подхода B** | Описание | ✅ |
```

### Общие правила для обоих форматов

- Номера задач берутся из имён файлов в `.tasks/` (например, `09-3-faq-content-pipeline.md` → `09-3`).
- Названия задач — **жирным** (`**текст**`), без точки на конце.
- Описания — краткие, без точки на конце.
- Отменённые задачи помечаются ↩️ / `Cancelled`, выполненные — ✅ / `Done`.

## 🔍 4. Выбор «самой сложной задачи»

Для раздела «Пример наиболее сложной задачи» выбирай задачу по приоритету:

1. Задача с наибольшим объёмом файла в `.tasks/done/`.
2. Задача, упомянутая в `.review/` как требующая доработки.
3. Задача с наибольшим количеством подзадач (например, `09-1` ... `09-9`).

Содержимое оборачивается в `::: details 📋 Посмотреть полностью ...` и включает:
- Полное описание проблемы.
- Код решения с VitePress-подсветкой (`// [!code ++]`, `// [!code warning]`).
- «Было / Стало» где применимо.

## 🛡️ 5. Sanitization — обязательная проверка перед публикацией

**После создания каждой страницы** обязательно проведи аудит на чувствительные данные.

### Что искать и заменять

| Тип данных | Пример | Действие |
|---|---|---|
| **Реальные API-ключи** | `DM_API_KEY = 'abc123...'` | Заменить на `'...'` |
| **Реальные числовые ID** | `DM_LIST_ID`, `97910` | Заменить на плейсхолдер `12345` |
| **Внутренние домены dev-стендов** | `shvedov.run.place` | Заменить на «внутреннем dev-окружении» |
| **Локальные file:/// ссылки** | `[file.txt](file:///c:/dev/...)` | Удалить или заменить на описание |
| **Email-адреса** | `user@company.ru` | Удалить или обобщить |
| **IP-адреса серверов** | `192.168.1.100` | Удалить или использовать `0.0.0.0` |

### Команды для быстрой проверки

После создания страницы запусти grep по созданным файлам:

```
grep -i "api.key\|secret\|password\|token" <файл>
grep -E "[0-9]{4,}" <файл>          # числовые ID > 999
grep -i "run\.place\|\.local\|localhost" <файл>  # dev-домены
grep "file:///" <файл>              # локальные ссылки
```

## ✅ 6. Финализация и верификация

### Чеклист перед завершением

1. ☐ Страница следует структуре из секции 2.
2. ☐ Карточка проекта содержит строку **Сайт** с внешней ссылкой.
3. ☐ Список задач оформлен таблицей (секция 3).
4. ☐ Есть раздел «Пример сложной задачи» в `::: details`.
5. ☐ Есть хотя бы одна пара `::: warning` → `::: tip` (сложности и решения).
6. ☐ Итоговые результаты — таблица метрик в `::: tip 🏆`.
7. ☐ Sanitization пройден (секция 5).
8. ☐ Страница добавлена в sidebar в `.vitepress/config.mts`.
9. ☐ `npm run docs:build` проходит без ошибок.

### Добавление в конфигурацию

Новые страницы добавляются в `sidebar` → `Доработка сайтов` → соответствующая CMS-группа:

```typescript
{
  text: 'WordPress',
  collapsed: false,
  items: [
    { text: 'Название кейса', link: '/ru/slug-название' }
  ]
}
```

### Валидация

Всегда завершай работу запуском сборки:

```bash
npm run docs:build
```

Сборка должна пройти без ошибок — это гарантирует, что все VitePress-контейнеры (`::: info`, `::: details`, `::: tip`, `::: warning`) корректно закрыты и не конфликтуют.
