# Стандарт оформления статей и портфолио в VitePress

Оформлять страницу как спокойный технический документ: сначала дать читателю краткую картину проекта, затем показать ключевые решения, после этого — полные исходные материалы. Сохранять высокую информационную плотность, но не превращать страницу в набор разноцветных плашек.

## 1. Рабочий процесс

1. Прочитать исходную статью, конфигурацию VitePress, тему и `package.json`.
2. Составить карту страницы: заголовки, контейнеры, code fences, таблицы, вложения, длинные исходники.
3. Проверить, какие возможности реально подключены. Не считать Mermaid, tabs или сторонний компонент доступными только потому, что их синтаксис встречается в Markdown.
4. Выбрать один визуальный язык: одинаковые `details`, статусы, подписи источников, таблицы и код.
5. Форматировать содержание без сокращения и переиначивания, если пользователь просит сохранить исходный текст.
6. Добавить только странично-изолированные стили через `pageClass`.
7. Выполнить синтаксический аудит, production-сборку и визуальную проверку на desktop и mobile.
8. Проверить локальную страницу и каждое скачиваемое вложение отдельным HTTP-запросом.

## 2. Анатомия страницы-кейса

Использовать следующий порядок, адаптируя его к фактическим материалам:

1. H1 с названием проекта.
2. Спокойная строка технологических `<Badge>` под H1.
3. Главный баннер или скриншот, только если он добавляет смысл.
4. `::: info` с карточкой проекта.
5. Обзор проекта и исходное ТЗ.
6. Полный реестр задач: выполнено / бэклог.
7. Наиболее сложная задача или ключевое архитектурное решение.
8. Проблемы и решения через `warning`, `tip`, при необходимости `danger`.
9. Итоговые результаты и QA-метрики.
10. Карта всех публикуемых материалов.
11. Полные исходные материалы в последовательности выполнения.

Для большой страницы ограничивать outline вторым и третьим уровнями, чтобы внутренние H4–H6 из исходников не перегружали правую навигацию:

```yaml
---
outline: [2, 3]
pageClass: project-case
---
```

## 3. Badge и контейнеры

### Badge

Использовать Badge для быстрого считывания технологии, типа материала или статуса:

- `tip` — готово, основной стек, успешный результат;
- `info` — имя файла, нейтральный тип материала;
- `warning` — бэклог, ограничение, число тестов;
- `danger` — критический риск или ошибка.

На узком экране длинный H1 с inline-Badge может переполнить страницу. Размещать стек отдельной строкой под H1:

```markdown
# Защита страницы `/contact/create`

<div class="case-tech-badges">
  <Badge type="tip" text="PHP" />
  <Badge type="warning" text="REST API" />
  <Badge type="info" text="Security & QA" />
</div>
```

В H2/H3 оставлять одну короткую статусную плашку:

```markdown
## 4. Полный набор QA test cases <Badge type="warning" text="152 кейса" />
```

### Контейнеры

- `::: info` — карточка проекта, контекст, карта материалов.
- `::: tip` — решение, результат, успешный QA.
- `::: warning` — проблема, ограничение, публичная sanitization-оговорка.
- `::: danger` — критический риск, уязвимость, потеря данных.
- `::: details` — полный исходник, большое ТЗ, длинный roadmap, QA-набор, код.

Не помещать каждый короткий абзац в отдельный контейнер. Чередовать контейнеры с обычными заголовками, списками и таблицами.

Карточку проекта оформлять таблицей с явными заголовками:

````markdown
::: info 📋 Карточка проекта

| Параметр | Значение |
|---|---|
| **Стек** | PHP, JavaScript, HTML/CSS |
| **Сроки** | 30 марта — 8 апреля |
| **Роль** | Разработка и архитектура решения |
| **QA** | 152 ручных тест-кейса |

:::
````

Не использовать строку `| | |`: VitePress покажет её как визуально пустую шапку таблицы.

## 4. Большие исходные материалы и details

### Сначала дать карту материалов

Перед серией длинных раскрывающихся блоков добавить компактный индекс:

````markdown
::: info 🧭 Карта материалов

| Раздел | Источник | Что внутри |
|:---:|---|---|
| **1** | `TASK.md` | Постановка и рабочий диалог |
| **2** | `ROADMAP.md` | Спринты, зависимости и DoD |
| **3** | `QA_TESTCASES.md` | Полный набор тест-кейсов |

:::
````

Нумерация в карте, H2 и тексте должна совпадать с реально опубликованными материалами. После удаления файла перенумеровать разделы и обновить заявленное количество материалов.

### Делать summary коротким

Не помещать полный путь в `summary`: он плохо читается и ломает мобильную компоновку. Оставлять действие в заголовке, а путь показывать первой строкой внутри:

````markdown
::: details 🗺️ Открыть полный roadmap проекта

<div class="case-source-path"><span>Источник</span><code>.tasks/done/project/ROADMAP.md</code></div>

Полное содержимое документа...

:::
````

Для каждой группы однотипных исходников использовать одну и ту же формулу summary: «Открыть полный…», «Открыть все…», «Открыть исходник…».

### Форматировать семантически, не переписывать

Если требуется сохранить содержание полностью:

- не сокращать, не улучшать формулировки и не исправлять фактические противоречия без запроса;
- менять только структуру Markdown, пунктуацию разметки и представление;
- оформить роли и реплики диалога отдельными заголовками, а исходные реплики — цитатами;
- превратить перечни в списки, хронологию — в таблицу, сравнение — в таблицу, зависимости — в `text`-дерево;
- оставить отсутствующие номера тестов отсутствующими; не додумывать строки;
- при sanitization заменить секреты, домены, имена, email, идентификаторы и реквизиты согласованными плейсхолдерами и явно отметить, что публичная версия очищена.

Не заключать целое ТЗ в огромный `text`-fence, если оно состоит из заголовков и списков. Такая «простыня» теряет типографическую иерархию и получает горизонтальный скролл.

### Списки статусов

Внутри `details` заменять несовместимые task-list markers, не меняя статус задачи:

```markdown
- ✅ **1.1** Выполненная задача
- ⬜ **1.2** Запланированная задача
```

Для большой программы работ использовать Badge в кратком реестре, а emoji-статусы — в полном исходнике.

### Акценты внутри details

По умолчанию не вкладывать VitePress-контейнеры друг в друга. Внутри `details` использовать заголовки, таблицы и цитаты:

```markdown
> **💡 Рекомендация.** Использовать поиск по уникальному идентификатору.

> **⚠️ Ограничение.** Проверка зависит от внешнего API.
```

## 5. Код, схемы и технические примеры

Всегда указывать язык открывающего code fence. Закрывающий fence должен состоять только из трёх обратных кавычек.

Для полного исходника добавлять имя файла и нумерацию строк:

````markdown
```php:line-numbers [csv-log-template.php]
function writeLog(array $row): void {
    // ...
}
```
````

Использовать:

- `php`, `html`, `javascript`, `json`, `apache`, `http` для кода и запросов;
- `text` для дерева директорий, ASCII-схемы, таймлайна или сериализованного значения;
- `[file.ext]` для подписи полного файла;
- `:line-numbers` для длинного исходника, но не для короткого фрагмента.

Не помещать inline Markdown внутрь `text`-fence: обратные кавычки там отображаются буквально. В ASCII-схеме писать `process.php`, а не `` `process.php` ``.

Для diff и подсветки использовать штатные маркеры Shiki:

````markdown
```php
$old = true;  // [!code --]
$new = true;  // [!code ++]
$critical = validate($value); // [!code highlight]
```
````

Если Mermaid renderer не подключён, заменить диаграмму без потери смысла:

- flowchart — вертикальной `text`-схемой;
- sequence diagram — таблицей «Шаг / Участник / Действие или ответ»;
- граф зависимостей — ASCII-деревом или таблицей «Этап / Зависит от / Результат».

Не называть сырой `mermaid` fence диаграммой: без renderer это только блок кода.

## 6. Таблицы, QA и метрики

Использовать таблицы для повторяющихся полей и точных сравнений:

```markdown
| Метрика | До | После | Улучшение |
|---|---:|---:|---:|
| SQL-запросы | 201 | 2 | **×100** |
| Время генерации | 1.4 сек | 0.08 сек | **×17.5** |
```

При переносе QA:

1. Не оставлять пустую строку посередине Markdown-таблицы — она завершит таблицу.
2. Не исправлять номера кейсов и результаты по догадке.
3. Сверить заявленное количество тестов с фактическими строками.
4. Показывать сводные метрики отдельно, а полные тест-кейсы — в `details`.
5. Проверить широкую таблицу на мобильном экране; разрешить горизонтальный скролл вместо сжатия текста до нечитаемого состояния.

## 7. Страничная стилизация

Не менять глобальный внешний вид документации ради одной статьи. Задать `pageClass` во frontmatter и ограничить все селекторы этой страницей:

```css
.project-case .vp-doc details {
  margin: 1rem 0 2rem;
  overflow: clip;
  border: 1px solid var(--vp-c-divider);
  border-radius: 14px;
  background: var(--vp-c-bg-soft);
  box-shadow: 0 8px 26px rgb(15 23 42 / 5%);
}

.project-case .vp-doc details > summary {
  padding: 1rem 1.1rem;
  color: var(--vp-c-text-1);
  cursor: pointer;
  font-weight: 650;
}

.project-case .vp-doc details[open] > summary {
  border-bottom: 1px solid var(--vp-c-divider);
  color: var(--vp-c-brand-1);
}
```

Использовать только переменные VitePress (`--vp-c-*`), чтобы оформление работало в светлой и тёмной теме.

Полезные страничные компоненты:

- `.case-tech-badges` — flex-строка технологий под H1;
- `.case-source-path` — компактная подпись источника внутри `details`;
- `.case-download-card` — карточка скачиваемого DOCX/PDF/архива;
- стили H4–H6 внутри `details` — спокойная иерархия длинного документа;
- чередование строк и нейтральная шапка у таблиц;
- рамка без лишней тени для блоков кода.

На ширине до `640px`:

- отключать sticky у `summary`;
- разрешать перенос длинных `code`-путей через `overflow-wrap: anywhere`;
- при необходимости выносить code-фрагмент H1 на отдельную строку;
- переводить download-card в две строки;
- проверять отсутствие горизонтального переполнения всей страницы.

Не делать дизайн аляпистым: один брендовый цвет, мягкий фон, один радиус карточек, максимум одна иконка на заголовок.

## 8. Скачиваемые файлы

Если пользователь просит дать оригинальный документ, не извлекать его в раскрывающийся текст без необходимости:

1. Скопировать очищенный файл в `public/files/<case>/`.
2. Дать прямую ссылку с `download`.
3. Учесть `base` из конфигурации VitePress. Для `base: '/cv/'` путь будет `/cv/files/...`.
4. Проверить имя файла, наличие в итоговом `dist` и HTTP `200`.
5. Не показывать удалённый шаблон в карте и нумерации, если пользователь просил оставить только заполненный отчёт.

Пример лаконичной карточки:

```html
<div class="case-download-card">
  <div class="case-download-card__body">
    <strong>QA Report · Pass</strong>
    <span>Заполненный отчёт ручного тестирования</span>
  </div>
  <a class="case-download-card__action" href="/cv/files/project/qa-report.docx" download>Скачать DOCX</a>
</div>
```

## 9. Критические VitePress gotchas

1. Не вкладывать обычные `:::`-контейнеры друг в друга. Если вложение действительно необходимо и проверено отдельно, использовать большее число двоеточий у внешнего контейнера (`:::: details` ... `::::`), но предпочитать плоскую структуру.
2. Не использовать `- [x]` / `- [ ]` внутри `details`; использовать `✅` / `⬜`.
3. Не оставлять Mermaid без установленного renderer.
4. Не использовать GitHub alerts `> [!TIP]`, `> [!WARNING]`, `> [!NOTE]` как замену VitePress-контейнерам. Внутри `details` использовать обычную цитату с жирным заголовком.
5. Не оставлять code fence без языка и не ставить язык на закрывающий fence.
6. Не помещать полный путь к файлу в `summary` длинного `details`.
7. Не использовать пустую строку заголовков Markdown-таблицы.
8. Не добавлять неподтверждённые данные ради заполнения пробелов в исходнике.
9. Не считать успешную сборку полноценной визуальной проверкой: CSS-переполнение и неудачная композиция могут собраться без ошибок.

## 10. Обязательная проверка

Перед завершением выполнить проверки, адаптировав путь к статье:

```bash
# Найти неподдерживаемую или подозрительную разметку
rg -n '^```mermaid|^> \[!|^- \[[ x]\]|^```$' ru/article.md

# Сверить число контейнеров при плоской структуре
rg -c '^::: (info|tip|warning|danger|details)' ru/article.md
rg -c '^:::$' ru/article.md

# Найти whitespace-ошибки
git diff --check

# Production-сборка
npm run docs:build
```

Дополнительно:

1. Проверить, что каждый opening code fence имеет язык, а каждый closing fence — чистый.
2. Открыть страницу локально и проверить ключевые закрытые и раскрытые `details`.
3. Сделать desktop-проверку примерно на `1440px`.
4. Сделать mobile-проверку примерно на `390px`.
5. Проверить таблицы, H1, длинные пути, source-path, download-card и горизонтальный скролл.
6. Проверить HTTP-коды страницы и вложений.
7. При наличии навыка `vitepress-dev` использовать его для build/dev/preview и сообщить пользователю фактический локальный URL.

Считать задачу завершённой только после успешной сборки и визуального контроля. Допустимо отдельно сообщить предупреждение о размере bundle, если оно не связано с разметкой страницы и сборка завершилась успешно.
